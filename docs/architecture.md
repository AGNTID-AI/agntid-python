# AgntID SDK — Architecture and Call Flow

> How the SDK connects AI agents to the AgntID runtime for per-prompt policy,
> audit, and tool-call correlation.

---

## 1. What the SDK does

The AgntID SDK sits between your agent framework and the AgntID MCP proxy.
It solves three problems:

1. **Task attribution** — every user prompt gets a unique `task_id` so the
   runtime knows which user said what.
2. **Tool-call correlation** — every tool call carries the `task_id` so the
   runtime can enforce policy and audit against the correct intent.
3. **Response sanitization** — platform-injected fields (`__agntid_*`) are
   stripped before the LLM sees them.

The SDK is framework-agnostic at its core. Framework-specific adapters
(currently MSK) live in optional submodules.

## 2. SDK structure

```
src/agntid/
  __init__.py        Public API, __version__
  client.py          AgntidMCPClient, get_tools_list, call_tool_async
  task.py            create_task, send_task_open, task_context, close_task
  mcp_wrapper.py     wrap_client — _task_id injection, __agntid_* stripping
  denial.py          Denial parsing, storage, formatting (framework-agnostic)
  util.py            require_env, format_tools_display
  _platform.py       Wire format: JSON-RPC message builders (spec 037)
  msk.py             Microsoft Semantic Kernel plugin builder (optional)
  py.typed           PEP 561 type marker
```

**Layers:**

| Layer | Modules | Purpose |
|-------|---------|---------|
| **Transport** | `client.py` | `AgntidMCPClient` wraps FastMCP so customer code has no direct `fastmcp` import |
| **Task lifecycle** | `task.py`, `_platform.py` | Generate `task_id`, send task open/close over MCP, async context manager |
| **Tool wrapper** | `mcp_wrapper.py` | Injects `_task_id` into every tool call, strips `__agntid_*` from responses |
| **Denial handling** | `denial.py` | Detects policy/task denials, parses structured JSON, formats human-readable summaries |
| **Framework adapters** | `msk.py` | Builds MSK kernel plugin from MCP tools; handles name sanitization, parameter schemas |
| **Utilities** | `util.py` | Environment checks, tool display formatting |

## 3. Key concepts

### 3.1 Task ID

A UUID generated by the SDK for each user prompt. It is the correlation key
that ties together:

- The **user** who issued the prompt
- The **agent** processing it
- The **prompt text** (intent)
- Every **tool call** made while fulfilling that prompt

```
task_id = agntid.create_task(agent_id, user_id, prompt)
```

The SDK always generates the `task_id` — the caller never supplies it.

### 3.2 Task open / close

| Event | When | What it tells the runtime |
|-------|------|---------------------------|
| **task_open** | Before any tool calls for a prompt | "Agent X is handling prompt Y for user Z; here is the task_id" |
| **task_close** | After the agent finishes the prompt | "This task is done; no more tool calls expected" |

Wire format (via MCP `tools/call`):

```
agntid_task_open  { task_id, agent_id, user_id, prompt }
agntid_task_close { task_id }
```

### 3.3 Wrapped client

`wrap_client(mcp_client, task_id)` returns a client that:

1. **Adds** `_task_id` to every tool call's arguments (the runtime uses it
   for correlation and policy, then strips it before the real tool sees it).
2. **Strips** any `__agntid_*` fields from the response (execution flow,
   policy decision, intent validation) so the LLM only sees tool output.

### 3.4 Denial handling

When the runtime denies a tool call (policy, guardrail, expired task), the
error payload contains structured JSON. The SDK:

1. **Detects** the denial (`is_denial_error`)
2. **Parses** it (`parse_denial_from_exception`) into a brief `user_msg`
   (for the LLM) and a structured `denial_info` dict
3. **Stores** it thread-locally (`set_last_denial`)
4. **Formats** it on demand (`format_denial`) for the human operator

## 4. Call flow — single user, single agent

This is the standard flow for one user prompt:

```
User                Agent (your code)           SDK                    AgntID MCP Proxy        Tool Server
 │                       │                       │                          │                       │
 │── prompt ──────────>  │                       │                          │                       │
 │                       │── create_task() ─────>│                          │                       │
 │                       │<── task_id ───────────│                          │                       │
 │                       │── send_task_open() ──>│── agntid_task_open ─────>│                       │
 │                       │                       │<── ok ──────────────────│                       │
 │                       │── set_task_id(tid) ──>│                          │                       │
 │                       │                       │                          │                       │
 │                       │── invoke LLM ─────────────────────────────────────────────────────────── │
 │                       │   LLM decides: call add_numbers(a=11, b=21)      │                       │
 │                       │── wrapped.call_tool ─>│                          │                       │
 │                       │                       │── add_numbers            │                       │
 │                       │                       │   { a:11, b:21,          │                       │
 │                       │                       │     _task_id: tid }  ───>│                       │
 │                       │                       │                          │── policy check ──────>│
 │                       │                       │                          │   (task_id → prompt    │
 │                       │                       │                          │    → user → policy)    │
 │                       │                       │                          │                       │
 │                       │                       │                          │   IF allowed:          │
 │                       │                       │                          │── add_numbers(a,b) ──>│
 │                       │                       │                          │<── result ────────────│
 │                       │                       │                          │   + __agntid_* fields  │
 │                       │                       │<── result ──────────────│                       │
 │                       │                       │   (strip __agntid_*)     │                       │
 │                       │<── clean result ──────│                          │                       │
 │                       │                       │                          │                       │
 │                       │   IF denied:           │                          │                       │
 │                       │<── denial exception ──│                          │                       │
 │                       │   (SDK stores denial,  │                          │                       │
 │                       │    returns brief msg   │                          │                       │
 │                       │    to LLM)             │                          │                       │
 │                       │                       │                          │                       │
 │                       │── task_context exit ─>│── agntid_task_close ───>│                       │
 │<── agent response ───│                       │                          │                       │
```

### What the runtime sees per tool call

| Field | Source | Purpose |
|-------|--------|---------|
| `_task_id` | SDK wrapper | Correlate this call to the task (and thus prompt + user) |
| `tool_name` | Agent/LLM | Which tool is being called |
| `arguments` | Agent/LLM | Tool parameters (minus `_task_id` which the runtime strips) |

### What the runtime returns (and SDK strips)

| Field | Purpose | Seen by LLM? |
|-------|---------|:---:|
| Tool result content | The actual tool output | Yes |
| `__agntid_execution_flow` | Step-by-step audit (guardrail, intent, policy) | No |
| `__agntid_policy_decision` | Policy evaluation details | No |
| `__agntid_error` | Denial reason | No |
| `__agntid_intent_validation_warning` | Intent mismatch info | No |

## 5. Multiple users (concurrent sessions)

Each user session runs its own prompt loop with its own `task_id` per prompt.
The SDK uses **thread-local storage** for denial state, so concurrent sessions
don't interfere.

```
User A (session 1)                  User B (session 2)
   │                                    │
   │── prompt "list buckets" ──>        │── prompt "add 11+21" ──>
   │   task_id = aaa-111                │   task_id = bbb-222
   │   agent_id = Agent1                │   agent_id = Agent1
   │   user_id = alice                  │   user_id = bob
   │                                    │
   │── tool: awsS3.list_buckets         │── tool: add_numbers
   │   _task_id = aaa-111               │   _task_id = bbb-222
   │                                    │
   │   Runtime correlates:              │   Runtime correlates:
   │   task aaa → alice → "list..."     │   task bbb → bob → "add..."
   │   Policy: alice's policies         │   Policy: bob's policies
```

**Key points:**

- `task_id` is unique per prompt, so the runtime never confuses calls between
  users — even if they call the same tool at the same time.
- `user_id` is set per task, so policies are evaluated against the correct
  user's permissions.
- Denial state is thread-local (`threading.local`), so user A's denial
  doesn't leak into user B's session.

## 6. Multiple agents on the same runtime

Different agents connect to the same AgntID MCP proxy. Each agent has its
own `agent_id` and creates its own tasks.

```
┌─────────────────────┐     ┌─────────────────────┐
│  Agent: FileBot      │     │  Agent: DataBot      │
│  agent_id: filebot   │     │  agent_id: databot   │
│  user_id: alice      │     │  user_id: alice       │
└────────┬────────────┘     └────────┬────────────┘
         │                           │
         │  task_id: ttt-111         │  task_id: ttt-222
         │  prompt: "upload X"       │  prompt: "query Y"
         │                           │
         ▼                           ▼
  ┌──────────────────────────────────────────┐
  │         AgntID MCP Proxy (ruse)          │
  │                                          │
  │  Task store (in-memory per instance):    │
  │    ttt-111 → filebot / alice / "upload"  │
  │    ttt-222 → databot / alice / "query"   │
  │                                          │
  │  Policy evaluation per tool call:        │
  │    tool + agent_id + user_id + prompt    │
  │    → allow / deny                        │
  └──────────────────────────────────────────┘
```

**Key points:**

- `agent_id` distinguishes which agent is making the call — policies can be
  scoped per agent (e.g. FileBot can access S3, DataBot cannot).
- The same `user_id` can appear across agents; the runtime evaluates the
  policy triple `(agent_id, user_id, tool)`.
- Each agent creates independent tasks; the runtime correlates tool calls to
  the correct task by `task_id`, not by connection or session.

## 7. Multiple tools within one task

A single prompt may trigger multiple tool calls. All share the same `task_id`:

```
Prompt: "List my S3 buckets and show the first object in each"
task_id: abc-123

  ┌─ tool call 1: awsS3.list_buckets     _task_id=abc-123 ─── policy ✓ ──→ result
  │
  ├─ tool call 2: awsS3.list_objects      _task_id=abc-123 ─── policy ✓ ──→ result
  │  (bucket_name=bucket-1)
  │
  ├─ tool call 3: awsS3.list_objects      _task_id=abc-123 ─── policy ✗ ──→ DENIED
  │  (bucket_name=restricted-bucket)
  │
  └─ task_close                           _task_id=abc-123

Runtime audit trail for task abc-123:
  prompt:  "List my S3 buckets and show the first object in each"
  user:    alice
  agent:   FileBot
  calls:   list_buckets (allowed), list_objects/bucket-1 (allowed),
           list_objects/restricted-bucket (denied by policy)
```

**Key points:**

- Every tool call in the prompt carries the same `task_id`.
- The runtime builds a complete audit trail: which tools were called,
  which were allowed, which were denied, and why.
- Policy evaluation happens per tool call, not per task — so one tool call
  can succeed while another in the same task is denied.
- If a tool is denied, the SDK stores the denial. After `agent.invoke()`
  returns, the caller can check `get_last_denial()` and show a formatted
  summary.

## 8. Policy enforcement flow

For each tool call, the runtime evaluates a pipeline:

```
Tool call arrives with _task_id
        │
        ▼
┌─ 1. Task resolution ─────────────────────────────────────┐
│  Look up task_id in the task store.                       │
│  If not found → deny ("Task expired or closed").          │
│  If found → extract agent_id, user_id, prompt.            │
└───────────────────────────────────────────────────────────┘
        │
        ▼
┌─ 2. Guardrail validation ─────────────────────────────────┐
│  Time windows, rate limits, etc.                           │
│  If failed → deny with guardrail reason.                   │
└───────────────────────────────────────────────────────────┘
        │
        ▼
┌─ 3. Intent parsing ──────────────────────────────────────┐
│  Does the tool call match the user's stated prompt?       │
│  Compares action + resource against prompt semantics.     │
│  If mismatch → warn (fail-open) or deny (fail-close).    │
└───────────────────────────────────────────────────────────┘
        │
        ▼
┌─ 4. Policy evaluation (OPA) ─────────────────────────────┐
│  Evaluate the tool action against the user's policies.    │
│  Input: agent_id, user_id, tool_name, server_id.          │
│  If denied → deny with policy name and reason.            │
└───────────────────────────────────────────────────────────┘
        │
        ▼
  Tool call forwarded to the real tool server
```

The SDK surfaces denials from any step as a structured `denial_info` dict
with fields: `reason`, `policy_name`, `intent_mismatch`, `denial_step`.

## 9. Wire format reference

### Task open (tools/call)

```json
{
  "jsonrpc": "2.0",
  "method": "tools/call",
  "params": {
    "name": "agntid_task_open",
    "arguments": {
      "task_id": "abc-123",
      "agent_id": "MyAgent",
      "user_id": "alice",
      "prompt": "List my S3 buckets"
    }
  }
}
```

### Task close (tools/call)

```json
{
  "jsonrpc": "2.0",
  "method": "tools/call",
  "params": {
    "name": "agntid_task_close",
    "arguments": {
      "task_id": "abc-123"
    }
  }
}
```

### Tool call (with _task_id injected by wrapper)

```json
{
  "name": "add_numbers",
  "arguments": {
    "a": 11,
    "b": 21,
    "_task_id": "abc-123"
  }
}
```

The runtime strips `_task_id` before forwarding to the tool server.

## 10. Integration summary

### For any agent framework

```python
import agntid

# 1. Connect
mcp_client = agntid.AgntidMCPClient(mcp_url)
async with mcp_client:
    tools = await agntid.get_tools_list(mcp_client)
    wrapped = agntid.wrap_client(mcp_client)

    # 2. Per prompt
    task_id = agntid.create_task(agent_id, user_id, prompt)
    async with agntid.task_context(mcp_client, task_id):
        await agntid.send_task_open_checked(mcp_client, task_id, agent_id, user_id, prompt)
        wrapped.set_task_id(task_id)

        # 3. Tool calls go through wrapped (your framework calls wrapped.call_tool_async)
        result = await wrapped.call_tool_async("tool_name", {"arg": "value"})

    # task_close sent automatically

    # 4. Check denial
    denial = agntid.get_last_denial()
    if denial:
        print(agntid.format_denial(denial))
```

### MSK-specific (adds kernel plugin)

```python
plugin = agntid.msk.create_plugin_from_mcp_tools(wrapped, tools)
kernel.add_plugin(plugin, plugin_name="MCPTools")
# Then use agent.invoke() as usual — all tool calls go through the wrapper
```

## 11. Salient features

| Feature | Description |
|---------|-------------|
| **Per-prompt task ID** | Every user prompt gets a unique UUID; all tool calls for that prompt are correlated |
| **Automatic task close** | `task_context` async context manager ensures close even on exceptions |
| **Transport abstraction** | `AgntidMCPClient` wraps FastMCP — no `fastmcp` import in customer code |
| **Response sanitization** | All `__agntid_*` fields stripped before the LLM sees them |
| **Denial formatting** | Structured JSON denials parsed into clean one-line messages for the LLM and detailed summaries for operators |
| **Framework-agnostic core** | Task lifecycle, wrapper, denial handling work with any Python agent framework |
| **MSK adapter** | One-call plugin builder with name sanitization and parameter schema mapping |
| **Thread-safe denial storage** | Thread-local storage so concurrent sessions don't leak denial state |
| **CLI-consistent examples** | Both MSK and OpenAI examples use identical `--agent-name`, `--user-id`, `--help` flags |
| **Build support** | `make build` produces versioned sdist + wheel; wired into root Makefile |
